A garbage collector exists to answer one question repeatedly: which objects on the heap can the program still reach? Everything else follows from that. The collector cannot know which objects the program will actually use again, so it approximates with reachability. An object is live if there is some chain of references from a root to it, and dead otherwise. Roots are the places execution can start following pointers from: the stack frames of every running thread, machine registers, static and global variables, JNI or FFI handles, and any internal structures the runtime pins. Anything not reachable from a root is provably unusable by the program, because there is no expression the program could evaluate that would produce a reference to it, so reclaiming it is safe.

The classic algorithm is mark and sweep, described by McCarthy in 1960 and still the backbone of most collectors. It runs in two phases. In the mark phase the collector starts from the roots and performs a graph traversal, setting a bit on each object it visits, either in a header word or in a separate side table of mark bits. The traversal uses an explicit work list rather than recursion, because object graphs can be deep enough to blow a native stack. In the sweep phase the collector walks the heap linearly from start to end, and every object without its mark bit set is dead: its memory goes onto a free list, and any finalisers or cleanup actions get queued. Mark bits are then cleared, or the sense of the bit is flipped so clearing is free.

Mark and sweep has two well-known problems. First, in its naive form the whole thing runs with the program stopped, and the mark phase costs time proportional to the number of live objects while the sweep costs time proportional to the size of the heap. A large heap therefore means a long pause. Second, sweeping leaves holes. Over time the heap fragments, so you can have a gigabyte free in aggregate and still fail to allocate a contiguous four-kilobyte array, and allocation degrades from a pointer bump into a search through free lists.

The alternative family fixes fragmentation by moving objects. Mark-compact adds a third phase that slides live objects down to one end of the heap, then updates every reference that pointed at them. Copying collection, in the Cheney formulation, divides the space in two and evacuates live objects from the "from" space into the "to" space during the traversal itself, leaving a forwarding pointer in the old location so subsequent references to the same object can be redirected. The cost of a copying collector is proportional only to the live data, not the heap size, and you get compaction for free, but you sacrifice half the address space and you must be able to find and rewrite every reference. That last requirement is why precise collectors need the runtime to know exactly which words are pointers, via object maps and stack maps emitted by the compiler; conservative collectors that guess by looking at word values cannot move anything, because they might rewrite an integer that merely looked like a pointer.

Generational collection is the single biggest practical win, and it rests on an empirical observation known as the weak generational hypothesis: most objects die young. In typical programs, the overwhelming majority of allocations become garbage almost immediately, while the objects that survive a while tend to keep surviving. If that holds, then repeatedly collecting the entire heap is enormous waste, because you keep re-marking the same long-lived objects that were live last time and will be live next time.

So the heap is partitioned by age. New objects are allocated in a young generation, often called the nursery or eden, which is small and collected frequently. A young collection, a minor GC, traces only from the roots into the young generation and evacuates the survivors, either into a survivor space or, once an object has survived some number of collections or the survivor space overflows, by promoting it into the old generation. Because nearly everything in eden is dead, the live set is tiny, and a copying collector over a tiny live set is extremely fast. Allocation itself becomes a pointer bump in a thread-local allocation buffer, which is a handful of instructions. The old generation is collected rarely, by a mark-sweep or mark-compact algorithm, in a major or full GC.

The complication is inter-generational references. If an old object holds a reference to a young one, a minor collection that traces only from the thread roots would wrongly conclude the young object is dead. Scanning the whole old generation to find such references would defeat the entire purpose. The solution is a write barrier: a small piece of code the compiler injects at every reference-storing field write, which records the fact that an old object now points somewhere younger. Implementations vary. A card-marking barrier divides the old generation into fixed-size cards, typically 512 bytes, and the barrier simply writes a byte into a card table to dirty the card containing the modified object. At collection time the collector scans only the dirty cards and treats the references it finds there as additional roots. Remembered sets are the more precise variant, recording per-region sets of incoming references, which is what region-based collectors need. Either way, you are trading a small constant cost on every pointer write, in exchange for making the common collection cheap. That trade is almost always worth it, which is why generational collection is near-universal in the JVM, .NET, V8, and modern Ruby and Python implementations.

Concurrent collection attacks the remaining problem: pause time. Even with generational collection, a full collection of a multi-gigabyte old generation stops the world for a long time, and for latency-sensitive services that is unacceptable. The goal is to do most of the collector's work while application threads, mutators in the literature, keep running.

This is harder than it sounds because the mutator can change the object graph underneath the collector. The standard analysis uses a tri-colour abstraction. Objects are white (not yet reached), grey (reached but whose fields have not yet been scanned), or black (reached and fully scanned). The collector's invariant is that no black object may point to a white object, because black objects will never be revisited, so such a pointer would let a live object be swept as garbage. A concurrent mutator can violate this by writing a reference to a white object into a black object's field and simultaneously deleting the only other path to that white object.

Barriers restore the invariant, and there are two broad strategies. Incremental-update barriers, exemplified by Dijkstra's, catch the write into the black object and re-greys either the source or the target, so the collector will revisit it. Snapshot-at-the-beginning barriers, associated with Yuasa, instead catch the overwritten reference before it is lost and shade the old target grey, effectively collecting against a logical snapshot of the heap taken when marking began. SATB is simpler to reason about and is what G1 and Shenandoah use; the cost is floating garbage, objects that died during the cycle but are retained until the next one.

Moving objects concurrently is harder still, because a mutator might read a reference while the collector is in the middle of relocating the object. The modern answer is a load barrier, sometimes called a read barrier: code inserted at reference loads that checks whether the reference points into a region currently being evacuated, and if so, either follows the forwarding pointer or performs the copy itself and updates the slot in place. ZGC uses coloured pointers, stashing metadata bits in unused high bits of the 64-bit address so the check is a mask and a branch, with multi-mapped virtual memory so the differently coloured addresses all resolve to the same physical page. Shenandoah historically used a Brooks forwarding word in every object header, and later moved to a load-reference barrier. Both achieve pause times in the sub-millisecond range that are independent of heap size, because the only stop-the-world work left is root scanning and a few short handshakes.

Region-based designs like G1 sit between the classic generational layout and this concurrent world. The heap is divided into many equally sized regions, each of which is dynamically designated eden, survivor, old, or humongous for very large objects. Marking is concurrent, but evacuation is a stop-the-world pause in which the collector selects a set of regions with the least live data, the garbage-first heuristic that gives the collector its name, and evacuates them within a pause-time budget the operator specifies. This is a soft real-time approach: rather than eliminating pauses, it makes their length controllable by choosing how much work to attempt.

None of these techniques is free, and the trade-offs are the actual engineering content. Concurrent collectors burn CPU on barriers and on collector threads that compete with application threads, so they typically reduce throughput by a few per cent in exchange for far better tail latency. Generational collectors pay a write barrier on every reference store and behave badly when the weak generational hypothesis fails, as with a large in-memory cache where objects are deliberately long-lived and promoted en masse. Copying collectors need headroom, and running a heap near capacity causes any collector to thrash, spending an escalating fraction of total time in GC. The practical implication for application code is mostly boring: allocation is cheap, short-lived garbage is close to free, large long-lived object graphs and finalisers are expensive, and the useful lever is usually heap sizing and collector choice rather than trying to outsmart the allocator.

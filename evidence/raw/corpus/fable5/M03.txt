When you run a query like SELECT * FROM users WHERE email = 'a@example.com' against a table with no index, the database has one option: scan every row and test the predicate. That's O(n) in the number of rows, and worse, it's O(n) in disk I/O, because every page of the table has to be pulled from storage. A B-tree index exists to turn that linear scan into a handful of page reads.

A B-tree is a balanced, ordered tree in which each node holds many keys, not just one. That fan-out is the whole trick. A node is sized to match a storage page, typically 4 to 16 KB, so a single node might hold hundreds of keys and child pointers. With a fan-out of, say, 500, a three-level tree addresses 125 million rows, and a four-level tree addresses tens of billions. In practice, the height of a B-tree over almost any real table is 3 or 4, so a lookup costs 3 or 4 page reads no matter how large the table grows. The root and inner nodes are hot and effectively always cached in memory, which means a typical indexed lookup touches disk once or twice, versus thousands of times for a full scan.

The lookup itself is a straightforward descent. Starting at the root, the engine binary-searches within the node to find which child's key range contains the target, follows that pointer, and repeats until it reaches a leaf. In the B+tree variant that virtually every database actually uses, the inner nodes hold only routing keys; the leaves hold the indexed values along with row locations (or the row data itself, in a clustered index). The engine then fetches the row from the heap or simply returns the leaf data.

Two properties beyond point lookups make B-trees the default index everywhere. First, the leaves are kept in key order and, in a B+tree, linked left to right, so range queries like WHERE created_at > '2024-01-01' or ORDER BY email become a single descent followed by a sequential walk along the leaf chain, which is exactly the access pattern disks and caches love. Second, the tree is self-balancing under writes: inserts that overflow a node split it and push a separator key upward, so the tree stays shallow and no rebuild is ever required, just a modest ongoing write cost.

That write cost is the trade-off to remember. Every index on a table is another B-tree that must be updated on every insert, update, and delete, and each descent for a write can dirty pages and cause splits. Indexes also only help when the query matches the key order, which is why a composite index on (last_name, first_name) helps a search on last_name but does nothing for a search on first_name alone. The mental model that serves you well: a B-tree buys you logarithmic reads with a small constant, paid for with extra work on every write.

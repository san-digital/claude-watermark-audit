Garbage collection exists to answer one question automatically: which objects can this program never touch again? Any object the program can still reach, through a variable, a field, a register, or a chain of references starting from one of those, must be kept. Everything else is garbage, and its memory can be reclaimed. The set of starting points is called the root set: static and global variables, each thread's stack slots, CPU registers, and handles held by the runtime itself. Every tracing collector, however sophisticated, is an elaboration on the same core move: start from the roots, follow every reference, and mark what you find. What differs is when the work happens, how it interleaves with the running program, and how the heap is organized to make the common case cheap.

The ancestral algorithm is mark and sweep. In the mark phase, the collector performs a graph traversal from the roots, typically with an explicit work list rather than recursion, setting a mark bit on every object it reaches. In the sweep phase, it walks the entire heap linearly and returns every unmarked object's memory to the free lists. The program, which GC literature calls the mutator because it mutates the object graph while the collector is trying to trace it, is traditionally paused for the duration; this is the classic stop-the-world collection. Mark and sweep is simple and handles cycles naturally, which is the fundamental advantage tracing has over naive reference counting: two objects pointing at each other but unreachable from any root are never found by counting references, but they are trivially skipped by tracing, since tracing enumerates the live set rather than the dead one. The weaknesses are equally clear. Pause times are proportional to heap size, sweeping touches memory that is mostly cold, and freeing objects in place fragments the heap, so allocation degenerates into hunting through free lists for a hole of the right size. A common refinement is mark-compact, which slides live objects together after marking, eliminating fragmentation at the cost of updating every reference to every moved object. Once objects can move, allocation becomes beautifully cheap: the free space is one contiguous region, and allocating is just bumping a pointer, a handful of instructions, about as fast as stack allocation.

Generational collection starts from an empirical observation so consistent it is called the weak generational hypothesis: most objects die young. The temporaries, iterator objects, boxed values, intermediate strings, and short-lived buffers that dominate allocation in real programs are dead almost as soon as they are created, while an object that has survived a few collections will probably survive many more. Generational collectors exploit this by segregating the heap by age. New objects are allocated in a small nursery (the young generation). When it fills, the collector traces only the nursery, and because most of its contents are dead, the cheapest strategy is to copy the few survivors out, either to a survivor space or, after enough survivals, to the old generation (this promotion is called tenuring), and then reset the nursery's allocation pointer. The cost of a young collection is proportional to the live data, not the space, so a nursery that is 90 percent dead is 90 percent free to collect. Minor collections therefore run in milliseconds while the old generation, collected rarely by a full mark-sweep or mark-compact, accumulates the long-lived survivors.

There is a catch, and it is the price of the whole scheme: an old-generation object may hold the only reference to a young object, so collecting the nursery alone would be unsound unless those old-to-young references are known. Scanning the old generation to find them would defeat the purpose, so the runtime tracks them as they are created, using a write barrier: a small piece of code the compiler emits alongside every reference store. The barrier typically records the modified location coarsely, in a card table that maps each few-hundred-byte chunk of the old generation to one byte, marking the card dirty. A minor collection then treats dirty cards, along with the usual roots, as additional starting points. Write barriers cost a few percent of mutator throughput, which is the standing tax generational collectors levy in exchange for short, frequent, cheap pauses.

Concurrent collection attacks the remaining problem: even generational collectors must eventually deal with a large old generation, and pausing for hundreds of milliseconds to trace it is unacceptable for latency-sensitive services. The idea is to run marking while the mutator keeps executing. The hazard is that the object graph changes underneath the tracer. The classic failure is described with the tri-color abstraction: objects are white (not yet seen), gray (seen, but their children not yet scanned), or black (fully scanned). Marking is complete when no gray remains; anything still white is garbage. A concurrent mutator can break this by storing a reference to a white object into an already-black object and then erasing every other path to that white object. The tracer, which never rescans black objects, will miss it and free a live object. All concurrent collectors prevent this with barriers. Insertion barriers (the Dijkstra style) intercept writes and shade the newly referenced object gray, so nothing white can hide behind black. Deletion barriers (the Yuasa style) shade the old target of an overwritten reference, preserving a snapshot of the graph as it existed when marking began. Some collectors instead use a read barrier, intercepting loads rather than stores, which is more expensive but enables the mutator to help with, or tolerate, concurrent relocation of objects.

In practice, production collectors combine all three ideas and differ in emphasis. HotSpot's G1 divides the heap into thousands of regions, marks the old generation concurrently, and then evacuates the emptiest regions in short incremental pauses, aiming at a user-supplied pause target. ZGC and Shenandoah go further and relocate objects concurrently too, using colored pointers or forwarding and load barriers, holding pauses under a millisecond even on terabyte heaps. Go's collector is non-moving, non-generational, and concurrent, betting everything on short pauses and a simple heap at some throughput cost. .NET's collector is generational with a concurrent background mode for its old generation. The trade space is always the same triangle: throughput (total mutator work per CPU-second), latency (pause length and frequency), and footprint (how much headroom the heap needs). Stop-the-world compacting collectors win throughput; concurrent collectors buy latency by spending barrier overhead and extra memory; generational designs make the everyday allocation path nearly free. Understanding which corner of that triangle your runtime has chosen, and which knobs move you along its edges, is most of what a working engineer needs to reason about GC behavior in production.

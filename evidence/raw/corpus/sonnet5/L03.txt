Garbage collection exists to solve a problem that every non-trivial program eventually runs into: memory gets allocated for objects that are used briefly and then abandoned, and if nothing reclaims that memory, the process eventually exhausts what the operating system has given it. Manual memory management, the malloc-and-free approach of C, hands that responsibility to the programmer, and decades of experience have shown that even careful, experienced engineers regularly get it wrong, either freeing memory too early, leading to use-after-free bugs and security vulnerabilities, or never freeing it at all, leading to slow, creeping leaks. A garbage collector automates this reclamation by figuring out, at runtime, which objects a program can no longer reach and therefore can never use again, and then recovering the memory those unreachable objects occupy.

The foundational technique underlying almost every modern collector is tracing, and the simplest form of tracing is mark and sweep. The collector starts from a known set of roots, which are the places a running program keeps direct references to objects: local variables on the stack, CPU registers, static or global variables, and a handful of other collector-specific bookkeeping structures. From each root, the collector walks the graph of references outward, following every pointer from an object to the other objects it points to, marking each object it visits, typically by setting a bit in the object's header or in a separate bitmap. This is the mark phase, and when it finishes, every object reachable from a root has been marked, and by construction every object that is not marked is garbage, because if the program could still reach it, the trace would have found it. The sweep phase then walks the entire heap linearly, and for every object that was not marked, it reclaims the memory, typically by adding it to a free list that the allocator can hand out again for future allocations, and it also resets the mark bits ready for the next cycle.

Mark and sweep is conceptually simple and handles cyclic data structures correctly, which is its major advantage over reference counting, the other classical approach to automatic memory management, where each object carries a count of how many references point to it and is freed the moment that count hits zero. Reference counting fails on cycles, because two objects that only reference each other will keep each other's count above zero forever even though nothing external can reach either of them, and working around that generally requires a supplementary cycle collector bolted on top, which is more or less a mark-and-sweep pass in disguise. The cost of plain mark and sweep, though, is that the sweep phase touches the entire heap on every collection, and the pause it causes, during which the rest of the program is typically stopped so that the object graph does not change underneath it, grows with heap size. For programs with large heaps and latency requirements, a naive stop-the-world mark and sweep quickly becomes unacceptable, which is why virtually every production-grade collector layers additional strategies on top of this basic idea rather than using it unmodified.

The first major refinement, and one that shows up in almost every mainstream managed runtime including the JVM, the CLR, and V8's collector for JavaScript, is generational collection. It rests on an empirical observation known as the generational hypothesis: in most real programs, the overwhelming majority of objects die young. Temporary objects created inside a loop iteration, short-lived request-handling objects in a server, intermediate results in a computation, these are allocated and become garbage almost immediately, while a much smaller set of objects, things like caches, long-lived data structures, and singletons, survive for a long time. Generational collectors exploit this by physically segregating the heap into at least two regions, commonly called the young generation and the old generation. New objects are allocated in the young generation, which is kept deliberately small so that collecting it is fast. When the young generation fills up, the collector runs a minor collection that traces only objects reachable from roots and from the old generation into the young generation, ignoring the much larger old generation entirely except as a source of roots via a mechanism usually called a remembered set or card table, which tracks the handful of places where an old object was mutated to point at a young one. Objects that survive a small number of these minor collections are promoted, or tenured, into the old generation on the theory that anything that has lived this long is likely to keep living. The old generation is collected far less often, using a full mark and sweep or a variant of it, because most of what it contains really is long-lived and a full trace of it would be wasteful to run frequently. The net effect is that the vast majority of collection work happens on a small, fast-to-scan young generation, and the expensive full-heap collections become rare events rather than the common case.

The second major refinement addresses the pause problem directly, and that is concurrent, or more precisely mostly-concurrent, collection. A stop-the-world collector, even a generational one, still has to pause the application threads, usually called mutators in this context because from the collector's point of view they mutate the object graph while it is trying to trace it, for at least the duration of the old-generation collections, and for latency-sensitive systems even a young-generation pause of a few milliseconds can matter. Concurrent collectors try to do most of the tracing and sweeping work while the mutator threads keep running, only pausing briefly at specific, carefully bounded points. The difficulty this introduces is real: if mutator threads are allowed to change the object graph, adding new references or dropping old ones, while the collector is in the middle of tracing it, the collector can end up with an inconsistent view and, in the worst case, incorrectly reclaim an object that is actually still reachable, which is a memory-safety bug just as serious as anything manual memory management can produce. Concurrent collectors solve this with mechanisms like write barriers, small pieces of code inserted by the compiler or runtime that run every time the mutator writes a reference into an object, which record enough information, often by marking the target object or logging the modified region, for the collector to account for changes it might otherwise miss. Algorithms in this family, such as the tri-color abstraction that classifies objects as white, meaning unvisited and provisionally garbage, grey, meaning visited but not yet fully scanned, and black, meaning fully scanned and confirmed live, formalise exactly which invariants a write barrier must preserve to guarantee correctness even as the mutator runs concurrently.

Production collectors such as G1 and ZGC on the JVM, or the concurrent mark-sweep style collectors used in browsers, combine generational structuring with concurrent or incremental marking and, in the more advanced designs, concurrent compaction as well, to keep pause times down to single-digit milliseconds even on multi-gigabyte heaps. Compaction matters here too: after enough sweep cycles a heap can end up fragmented, with free memory scattered in small gaps between surviving objects rather than available as one large contiguous block, which can eventually cause allocation of a large object to fail even though the heap technically has enough free space in total. Compacting collectors deal with this by relocating surviving objects so they sit next to each other, squeezing all the free space into a single region, though this in turn means updating every pointer anywhere in the heap that referred to an object's old address, which is its own substantial piece of engineering. Understanding these three ideas together, tracing as the basis for correctness, generational structuring as the basis for throughput, and concurrency as the basis for low latency, gives you a working mental model for almost any garbage collector you will encounter in production, along with a decent intuition for why the tuning knobs your runtime exposes, heap sizing, generation ratios, and pause-time targets, exist and what trade-offs they are actually making on your behalf.

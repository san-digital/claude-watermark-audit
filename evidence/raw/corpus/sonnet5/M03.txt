A B-tree index speeds up database lookups by organizing keys into a balanced, multi-way tree structure that keeps the number of disk reads needed to find a row small, even as a table grows into the millions of rows. Unlike a binary tree, where each node has at most two children, a B-tree node typically holds many keys and many children, often hundreds, depending on the page size the database engine uses to read data from disk. This wide branching factor is the whole point: because each node can be packed with so many keys, the tree stays shallow. A table with millions of rows might only need a tree three or four levels deep, meaning a lookup that would otherwise require scanning the entire table instead touches only three or four pages.

When you query a column with a B-tree index, the engine starts at the root node and compares your search value against the keys stored there to decide which child pointer to follow. It repeats this comparison at each level, narrowing the range of possible matches at every step, until it reaches a leaf node containing the actual row pointers or, in the case of a clustered index, the row data itself. Because internal nodes only store keys and pointers rather than full rows, they are small enough that entire levels, or even the whole upper portion of the tree, can be cached in memory, making repeated lookups very fast.

B-trees also keep themselves balanced automatically as data is inserted or deleted. When a node fills up and a new key needs to be inserted, the node splits into two and a key is pushed up to the parent; if that causes the parent to overflow, the split cascades upward, occasionally growing the tree by one level at the root. Deletions work in reverse, merging or borrowing keys from sibling nodes to keep every node reasonably full. This self-balancing behaviour guarantees that lookup, insertion, and deletion all cost roughly the same, predictable amount of work no matter how the data was inserted, which is why B-trees remain the default index structure in most relational databases.

The other major benefit is that B-trees preserve key order, so they support not just exact-match lookups but range queries, sorting, and prefix searches efficiently, which is exactly the kind of query pattern that shows up constantly in real applications, from filtering by date range to paginating results.

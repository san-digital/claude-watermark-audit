## 3. Method and exact commands (reproducible)

Tools (stdlib-only Python 3.11.8, unicodedata UCD 14.0.0):

- `scripts/scan_unicode.py` -- per-file SHA-256 of raw bytes, full code point
  inventory (U+XXXX, Unicode name with UCD-14 fallback, category, UTF-8 hex,
  counts, positions capped at 200 with cap recorded), escaped +-30-char context for
  flagged occurrences, nearest-ASCII comparison, NFC/NFD/NFKC/NFKD report with
  per-form SHA-256, mixed-normalization detection, and one-primary-bucket
  classification. Invisible/hidden buckets and the typographic bucket are
  structurally separate and never merged.
- `scripts/compare_bytes.py` -- SHA-256/length/identity, byte-level and
  character-level diffs, and per-difference classification
  (`line-ending`, `trailing-whitespace`, `invisible-character`,
  `typographic-substitution`, `normalization`, `other`).

Commands actually executed:

```
# validation suite (output captured verbatim in tests/TEST-OUTPUT.txt)
cd <BASE> && python3 -m unittest discover -s tests -v 2>&1 | tee tests/TEST-OUTPUT.txt

# representative single-file scans (human-readable and JSON)
python3 scripts/scan_unicode.py evidence/raw/corpus/opus5/S01.txt
python3 scripts/scan_unicode.py --json evidence/raw/corpus/fable5/L07.txt

# route comparison, e.g. the pty route
python3 scripts/compare_bytes.py --json evidence/routes/unicode_probe__R0_source.txt \
    evidence/routes/unicode_probe__R4_pty_terminal.txt

# full corpus sweep: a driver that calls scan_unicode.scan_file() /
# compare_bytes.compare_files() over every corpus, control and route file and
# aggregates counts and rates (kept in the session scratchpad; every number
# below regenerates from the two scripts above run over the same paths)
python3 <scratchpad>/aggregate_scan.py
```

The driver adds nothing analytical: it only iterates the two instruments over the
file set and sums bucket counts. Any single number below can be re-derived with a
one-file `scan_unicode.py` invocation.

## 8. Normalization findings

- **All 120 model files, all 5 human controls and all 5 synthetic controls are
  already in NFC form** (`unicodedata.is_normalized("NFC") = true`; NFC SHA-256
  equals original SHA-256 for every file).
- **No file anywhere exhibits mixed NFC/NFD normalization.**
- Model corpora are additionally NFKC-stable: NFKC output is byte-identical to the
  original for all 120 files (no compatibility characters at all).
- The human control differs under NFKC/NFKD only where expected: Project
  Gutenberg boilerplate contains U+2122 TRADE MARK SIGN (x85, all five files),
  which NFKC folds to "TM". NFD differs wherever precomposed accents exist, in
  corpus and control alike -- an arithmetic consequence of NFC text, not a finding.

Uniform NFC is consistent with UTF-8 text produced from a tokenizer vocabulary
trained on predominantly NFC web text; it provides no watermark signal.

## 11. Detector sensitivity and honest blind spots

What this scanner **would have caught** (each proven by a passing positive
control): any zero-width/invisible character, bidi control or isolate, Unicode tag
character (with payload decoding), variation selector, unexpected C0/C1/Cf/Co
control, combining-mark abuse, Cyrillic/Greek homoglyph inside a Latin word,
non-ASCII space variant *present in the file*, mixed or unusual normalization, and
any byte-level alteration between two copies of a text.

What it **would NOT have caught**:

1. **Space-variant marking stripped before disk.** Proven blind spot: the
   collection link converts U+00A0/U+202F/U+2009/U+2003/U+2002/U+3000 to U+0020
   (0 of 6 survived, twice). If a model marked text with space variants, this
   corpus would show nothing. Note the asymmetry: this is a genuine hole for
   space-based marking specifically, while zero-width/bidi/tag/VS/homoglyph
   marking is demonstrably detectable and demonstrably absent.
2. **Token-selection (statistical) watermarks.** A watermark carried in the
   *choice* among ordinary words/tokens leaves no unusual characters whatsoever.
   Character-level forensics is structurally blind to it. The zero findings above
   are therefore NOT proof that no watermark exists -- only that no
   character-layer watermark reached disk.
3. **Formatting-pattern channels within ordinary ASCII** (e.g. a code hidden in
   line-break positions, synonym choice, or punctuation placement). The scanner
   reports the characters faithfully but has no distributional model;
   whitespace-pattern channels were partially bounded here by the explicit
   trailing-whitespace/CR/TAB/double-space sweep (all zero), but subtler layout
   codes remain out of scope for this instrument (they belong to the statistical
   subagent).
4. **Anything upstream of the Write tool** other than what the positive controls
   exercise (e.g. characters the sampling API could emit but the harness refuses
   to pass through in categories we did not probe).

## 13. Bottom line

At the character and byte layer, the 120-file corpus is **cleaner than the human
control**: no hidden characters of any class, uniform NFC, pure LF, no trailing
whitespace, and full compliance with ASCII-only prompts -- measured with an
instrument whose positive controls prove it would have seen every one of those
categories had they been present, through a pipeline proven to deliver them. Two
honest limits stand: space-variant marking is unobservable through this
collection path, and a watermark carried purely in token selection would leave no
character-level trace at all. Absence of hidden Unicode is evidence against
character-layer watermarking only, not against watermarking in general.
